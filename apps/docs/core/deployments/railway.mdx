This fork runs as a **single container** with a local libSQL database, so a Railway deployment is one service plus a volume. There is no PostgreSQL plugin and no separate web service.

## Deploy from the repository

1. Create a Railway project and choose **Deploy from GitHub repo**, selecting this fork.
2. Railway detects `Dockerfile.kaneo` as the build file.
3. Add a **volume** mounted at `/app/data` — it holds `kaneo.db` and its WAL/SHM sidecars.
4. Set the service's public port to **5173** and generate a domain.
5. Set the environment variables:

```env
KANEO_CLIENT_URL=https://your-domain.example
AUTH_SECRET=                             # openssl rand -hex 32
```

`KANEO_API_URL` defaults to `KANEO_CLIENT_URL/api`, so one public domain is enough: the container proxies `/api` requests to the internal API process.

6. Deploy. The health check is `GET /api/health` on port 5173.

## Post-deployment setup

1. Open the public URL and create the first account.
2. Configure a custom domain if you want one.
3. Optionally set up SSO, object storage, or the MCP endpoint — see the [environment variables](/core/installation/environment-variables).

## Notes

- The volume is required: without it, the database is recreated on every deploy.
- Railway's usual `PORT` variable is not used; the container always listens on 5173 (nginx front, bundled API behind it).
- For backups, read or copy `kaneo.db` (plus its `-wal`/`-shm` sidecars) from the mounted volume.
