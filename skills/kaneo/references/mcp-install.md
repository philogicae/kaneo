# MCP Installation

The skill operates **through** the instance's built-in HTTP MCP endpoint. Connect the agent host first; without a working connection, the tools described in [mcp-guidelines.md](mcp-guidelines.md) are not callable.

## Endpoint

| Instance setup             | Endpoint                                |
| -------------------------- | --------------------------------------- |
| Web and API on one origin  | `https://<instance>/api/mcp`            |
| API hosted on its own host | `https://<api-host>/api/mcp`            |

The endpoint is Streamable HTTP — no extra process or package. The instance's account settings (Settings → Account → MCP) shows the exact URL and per-host commands for the deployment; prefer that generated value over a hand-written one.

## Authentication

- **OAuth 2.1 + PKCE (preferred):** the first connection opens a consent page in the browser. After approval, all tools run as that user. Discovery lives under `/.well-known/oauth-protected-resource/api/mcp` and `/.well-known/oauth-authorization-server/api`.
- **API key:** created in Settings → Account → Developer. Send `Authorization: Bearer <key>` or `x-api-key: <key>`. Revoking the key revokes MCP access immediately.

An MCP connection grants no extra permissions: the tools are bounded by what the signed-in account can already do in the REST API.

## Host configuration

Use the configuration generated by the instance's MCP settings page. Common shapes:

| Host        | Setup                                                                                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------ |
| Claude Code | `claude mcp add --transport http kaneo <url>`; add `--header "Authorization: Bearer <key>"` for an API key    |
| Codex       | `codex mcp add kaneo --url <url>`; TOML `[mcp_servers.kaneo]`; `codex mcp login kaneo` for OAuth              |
| Gemini CLI  | `gemini mcp add --transport http kaneo <url>`; the JSON entry uses `httpUrl`                                  |
| OpenCode    | `opencode.json`: `mcp.kaneo` with `type: "remote"` and `url`; `opencode mcp auth kaneo` for OAuth             |

## Verify the connection

1. `whoami`: confirm the expected account.
2. `list_workspaces`: confirm the intended workspace is visible.
3. If a tool from the catalog is missing, the client may target an older deployment. Refresh the catalog and report the gap; do not invent tool names or call REST routes as a substitute.

## Skill bundle over HTTP

The instance also serves the skill bundle, so a host can install it without a repository checkout:

- `GET /api/skills/kaneo/skill.md` — this entry point. Agents and `curl` receive the raw markdown including the YAML frontmatter (`name`, `description`, `version`).
- `GET /api/skills/kaneo/references/<file>.md` — reference files (`lifecycle`, `mcp-guidelines`, `setup`, `mcp-install`).

These routes are public — the bundle is documentation, never workspace data. Browsers receive a rendered HTML page; agents should keep the default `Accept` header (or request `text/markdown`) to receive the exact files.

## Troubleshooting

- A `401` from `/api/mcp` without credentials is expected.
- A `404` usually means a reverse proxy is not forwarding `/api/mcp` or the `/.well-known` discovery paths.
- API-key failures most often mean a revoked key or one without workspace access; issue a new key instead of reusing an old one.
- Permission errors are decided server-side. Ask an administrator to review the account's workspace role; never change roles or settings to force an operation through.
